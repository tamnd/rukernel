# Boot and platforms

A kernel that matches Linux's system calls but cannot boot the way Linux boots is not a replacement. The boot protocols, the kernel command line, the initramfs format, the firmware interfaces and the architectures are all part of what distributions, bootloaders and cloud images assume.

## 15.1 Architectures

| Architecture | Status | Why |
|---|---|---|
| x86-64 | tier 1 from R0 | servers, desktops, clouds, the compat and bench reference |
| arm64 | tier 1 from R4 | Graviton, Ampere, Axion and Cobalt clouds, Apple Silicon under Asahi, Snapdragon X laptops, phones |
| riscv64 | tier 2 from R8 | the RVA23 profile hardware arriving in 2026, and Linux's growing support |
| x86 (32 bit), arm (32 bit) | user space only, as compat ABIs | 32 bit binaries run on 64 bit kernels (section 15.2); no 32 bit kernel |
| loongarch64, powerpc64le, s390x | out of scope at 1.0 | listed in document 24 |

"Tier 1" means: the full compat suite and the full bench suite run on that architecture every night, and a regression there blocks a release.

## 15.2 Compat ABIs

Linux runs 32 bit binaries on 64 bit kernels, and some important programs still are 32 bit:

- Steam's client until recently.
- Old games.
- Proprietary tools.
- Wine before 11. Wine 11's WoW64 removes most of the Windows side of this need (document 16.3).

rukernel implements:

- **ia32 on x86-64**: the `syscall_32.tbl` numbers, `int 0x80` and `sysenter` and `syscall` entry, the compat structure layouts (generated by `rk-abigen` from the same headers built for i386), 32 bit signal frames, and the 32 bit vDSO.
- **x32**: the 36 x32 specific entries at 512 to 547, and the x32 ABI flag. Rarely used, but defined.
- **AArch32 on arm64**, on CPUs that still support it, which excludes most 2025 and later cores and all Apple Silicon.

Compat is generated rather than hand written. `rk-abigen` produces the 32 bit layouts and the conversion code between compat and native structures. That is the class of code where Linux has had most of its `compat_*` bugs, because the conversions are written by hand there.

## 15.3 Boot protocols

**x86-64:**

- The Linux boot protocol (`bzImage` with the setup header, version 2.15).
- The EFI stub (the kernel image is a PE/COFF executable that UEFI can load directly).
- The zboot format for compressed EFI images.
- The 64 bit entry used by direct kernel boot in QEMU, Firecracker and Cloud Hypervisor, including PVH for the Xen and minimal VMM path.

**arm64:**

- The arm64 `Image` header.
- The EFI stub.
- Device tree and ACPI boot.

**riscv64:** the RISC-V `Image` header and the EFI stub, with SBI for firmware calls.

**What this enables.** A rukernel image is a drop in replacement for `vmlinuz`. GRUB, systemd-boot, the UKI (unified kernel image) format with `ukify`, rEFInd, the Raspberry Pi firmware, U-Boot, Asahi's m1n1 and U-Boot chain, iPXE network boot, and the cloud providers' direct boot paths all load it unchanged.

**Command line.** Linux's parameters, parsed with the same rules: quoting, `--` for init arguments, and `param.subparam=` for built in "modules". The parameters distributions and admins set are honoured with Linux's meaning: `root=`, `rootflags=`, `rootfstype=`, `ro`, `rw`, `init=`, `rdinit=`, `console=`, `earlycon=`, `quiet`, `loglevel=`, `mitigations=`, `nokaslr`, `iommu=`, `intel_iommu=`, `amd_iommu=`, `hugepages=`, `isolcpus=`, `nohz_full=`, `rcu_nocbs=`, `cgroup_no_v1=`, `systemd.*` (passed through), `lsm=`, `selinux=`, `apparmor=`, `ima_*` and `crashkernel=`. Unknown parameters are passed to init as Linux does, and `/proc/cmdline` reads the same.

**initramfs.** The newc cpio format, compressed with gzip, zstd, xz, lz4 or bzip2, concatenated archives, the builtin initramfs, and microcode early loading from the first uncompressed archive. dracut, mkinitcpio, initramfs-tools and systemd's initrd all produce images that rukernel boots.

**kexec and crash dumps.** `kexec_load` and `kexec_file_load`, so rukernel can kexec Linux and Linux can kexec rukernel. That gives a way to switch kernels without a reboot through firmware, and a useful test. A crash kernel with `/proc/vmcore` in the ELF format makedumpfile and crash read. The crash utility needs Linux's internal structures, so it does not understand rukernel's memory. rukernel ships its own vmcore reader, `rkcrash`, and that difference is listed.

## 15.4 Firmware interfaces

- **UEFI runtime services:** variables through efivarfs, time, the capsule update interface for fwupd, and the EFI memory attributes table.
- **ACPI:** the table parser for every table Linux uses (MADT, FADT, DSDT and SSDTs, MCFG, SRAT, SLIT, HMAT, IORT, DMAR, IVRS, SPCR, BGRT, CEDT for CXL, PPTT and others), and an AML interpreter. Linux uses ACPICA, a portable C library under a dual licence. rukernel writes its own AML interpreter in Rust, the way the `acpi` and `aml` crates do, with ACPICA's test suite (ASLTS) as the oracle. An AML interpreter is one of the most exposed pieces of a kernel, because firmware AML is notoriously buggy and occasionally hostile, and safe Rust removes the class of memory errors there. It also exposes `/sys/firmware/acpi/tables`, the ACPI events through netlink, and the platform profile interface.
- **Device tree** with the full binding set for the supported arm64 and RISC-V platforms, plus `/sys/firmware/devicetree` and `/proc/device-tree`.
- **SMBIOS and DMI** in `/sys/class/dmi/id` and `/sys/firmware/dmi`. Many programs read it: systemd-detect-virt, dmidecode, cloud-init and licence managers.
- **PSCI, SDEI and the SMCCC firmware calls** on arm64, and **SBI** on RISC-V.

## 15.5 IOMMU and DMA

Intel VT-d, AMD-Vi, the Arm SMMUv3, the RISC-V IOMMU and virtio-iommu. DMA translation is on by default, in strict mode for untrusted devices (Thunderbolt and external ports) and in lazy flush mode elsewhere, matching Linux's defaults. Changing that changes I/O performance, so the bench harness pins the mode on both kernels. The IOMMU is also what isolates devices from memory a driver did not map, and it is what makes VFIO passthrough and the driver host (document 12.5) safe. IOMMUFD is the user space interface for VMMs.

The IOMMU page table code and the invalidation queue are in `rk-frame`. They are page table code like the CPU's, verified with the same Verus framework (document 20).

## 15.6 x86 platform specifics

- **FRED** (Flexible Return and Event Delivery). Linux enables it by default since 7.1 on CPUs that have it (Intel Panther Lake and later). It replaces the IDT, `syscall` and `sysret` with a cleaner event delivery model and is faster on the system call path. rukernel supports FRED from the start on capable hardware, with the IDT path for the rest. Both entry implementations live in `rk-frame`.
- **CET:** user shadow stacks (`map_shadow_stack`, `arch_prctl(ARCH_SHSTK_*)`, glibc's enablement), supervisor IBT for the kernel, and the shadow stack token in signal frames.
- **FSGSBASE** user instructions, which Wine and Java use.
- **AMX** and AVX-512 state management with `arch_prctl(ARCH_REQ_XCOMP_PERM)` dynamic feature enablement, and the XSAVE signal frame layout including its size growth, since `sigaltstack` sizes are computed from `AT_MINSIGSTKSZ`.
- **LAM** (linear address masking) and the `ARCH_ENABLE_TAGGED_ADDR` interface.
- **Split lock detection**, **UMIP** emulation for the old instructions Wine needs, and **TSX** control.
- **Confidential guest support:** TDX and SEV-SNP guest boot (`tdx_guest`, `sev_guest` devices, and attestation reports through the `configfs-tsm` interface). rukernel as a confidential guest is an early target, because a small, memory safe guest kernel is exactly what confidential computing wants, and the device set is only virtio.

## 15.7 arm64 platform specifics

- Pointer authentication and BTI for user space, with the `PR_PAC_*` prctls.
- MTE for user space (`PROT_MTE`, `PR_SET_TAGGED_ADDR_CTRL`).
- SVE and SME state with `PR_SVE_SET_VL` and `PR_SME_SET_VL`, and the signal frame records.
- GCS (Guarded Control Stack), the arm64 shadow stack, with its prctls.
- The vDSO with the arm64 counters.
- **The TSO prctl.** Apple Silicon has a per thread hardware TSO mode (`ACTLR_EL1.TSOEN`). Asahi exposes it to user space as `PR_SET_MEM_MODEL`, which FEX uses to run x86 code with x86 memory ordering at full speed. rukernel offers the same prctl on hardware that has it, and makes it a no-op that reports failure elsewhere (document 16.5).

## 15.8 Targets, in the order they are supported

1. QEMU/KVM q35 and virt (arm64), with virtio. This is the development and compat target.
2. Firecracker and Cloud Hypervisor, which have a minimal device set and are the guest kernel role.
3. The public clouds: AWS (Nitro: ENA, NVMe), Google Cloud (gVNIC, NVMe), Azure (Hyper-V VMBus with MANA networking), and Oracle and Hetzner (virtio).
4. Bare metal x86 servers (document 12.3).
5. Bare metal arm64 servers: Ampere Altra and AmpereOne.
6. Laptops: Framework 13 (AMD), ThinkPad X1 Carbon (Intel), and Apple M1 and M2 under Asahi's boot chain. The Asahi drivers' designs, for AGX, DCP, the SMC and the audio codecs, are the reference for Apple platform drivers. M3 support landed in Asahi's installer in September 2026, without GPU acceleration, and rukernel follows Asahi's hardware support rather than leading it.
7. RISC-V boards and servers implementing RVA23.

## 15.9 Power management

Suspend to idle (s2idle) and suspend to RAM (S3) where firmware supports it, hibernation to swap with the same image header, so a rukernel hibernation image is resumable only by rukernel, and that is detected. Runtime PM of devices, CPU frequency scaling with `schedutil` driven by the scheduler's utilization signal, and cpuidle states. Laptop battery life is a bench row in the desktop profile: idle power draw over 30 minutes on the reference laptops, on both kernels.
