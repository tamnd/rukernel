# Repository and crate layout

Three repositories, following the rucc family. The kernel is a Cargo workspace of many small crates with a strict layering rule. The harnesses are ordinary Rust command line programs with data directories.

**Profiles.** A profile chooses Cargo features: which file systems, drivers and personas are built in. `guest` is virtio only and is the Firecracker and Kata image. `server` adds bare metal server drivers. `desktop` adds GPUs, Wi-Fi, audio and personas. `rk-config` also reads a Linux `.config` and enables the rukernel features that correspond to the enabled Linux options, then writes the generated `/proc/config.gz` (document 03.8). A distribution can keep its Kconfig fragments as the source of intent.

## 23.2 The layering rule

Crates are layered, and a crate may depend only on crates in the same or lower layers:

| Layer | Crates |
|---|---|
| 0 | `rk-frame`, `rk-abi`, `rk-lib`, `rk-macros`, and the 23.3 leaf crates |
| 1 | `rk-time`, `rk-sched`, `rk-mm`, `rk-sec` (core) |
| 2 | `rk-proc`, `rk-ns`, `rk-ipc`, `rk-vfs`, `rk-block`, `rk-net`, `rk-drv-core`, `rk-bpf` |
| 3 | file systems, protocols, drivers, LSMs, `rk-uring`, `rk-kvm`, `rk-netfilter`, `rk-bpf-*` |
| 4 | `rk-persona`, `rk-mach`, `rk-ntsync`, `rk-nt`, `rk-drvhost` |
| 5 | `rk-syscall` (dispatch to everything), `rukernel` (the binary) |

Cycles that Linux has (the VFS calls into mm, which calls back into the VFS for writeback) are broken with traits defined in the lower crate and implemented in the higher one. For example, `rk-mm` defines `trait AddressSpaceOps`, and `rk-vfs` implements it. `cargo-deny` and a custom lint check the layer table on every build.

## 23.3 The unsafe rule and the audited leaf crates

**The rule.** Every crate has `#![forbid(unsafe_code)]` at its root, except `rk-frame` and the crates in this list. The build checks it with a script over `cargo metadata` and the crate roots, not just by convention. Adding a crate to the list needs a written justification, a named owner and an audit, recorded in `frame/AUDITED.md`.

**The list at 1.0, kept short:**

| Crate | Why it cannot be safe | Size budget |
|---|---|---|
| `rk-intrusive` | intrusive linked lists and red black trees (wait queues, runqueues, LRU lists) without allocation, as Linux uses everywhere; safe wrappers with pinned nodes | 2,000 lines |
| `rk-crypto-arch` | AES-NI, VAES, SHA and ARMv8 crypto through `core::arch` intrinsics, which are `unsafe` to call | 3,000 lines |
| `rk-checksum-arch` | vectorized checksums and CRCs (internet checksum, crc32c, crc64) for networking and file systems | 1,000 lines |
| `rk-memops` | `memcpy`, `memset`, `memmove` and `copy_page` tuned per CPU (`rep movsb` with ERMS and FSRM), which the compiler builtins call | 1,000 lines |
| `rk-zerocopy-ext` | layout assertions that `zerocopy` cannot yet derive for some uAPI unions; shrinks as `zerocopy` grows | 500 lines |

**Third party crates** that contain `unsafe` are allowed only from a vetted list: `zerocopy`, `bitflags`, `hashbrown` (with the kernel allocator, as a backing table), `intrusive-collections` (if adopted instead of `rk-intrusive`), `gimli` for unwinding and debug info, and `object` for ELF parsing. Each version bump is reviewed with `cargo-vet`, the same way the kernel's own audited crates are.

**Counting.** `rk-frame` plus the leaf crates are reported per release in lines of code and in `unsafe` blocks. The budget is in document 02.4.

## 23.6 Conventions shared by all three

- Plain English, one paragraph per line, no em or en dashes, in every README and doc.
- Commit messages in the imperative, with a subsystem prefix (`rk-mm: batch COW in fork`).
- No generated file is edited by hand. Generated files carry a header naming their generator and inputs.
- Every pull request to `rukernel` runs the per PR compat set (document 18.9) and the per PR bench cells for the subsystems it touches (document 19.7).
